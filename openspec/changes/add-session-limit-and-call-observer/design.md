## Context

在途上限约束会话两端各自未完成的请求数，流也占一个名额。双方必须对它有一致的理解：一端发出的请求多于另一端的上限，会话即以协议错误结束。因此它不能只是宿主一侧的选项。

## Decisions

### 宿主选择，初始化时告知

宿主在 `Options.Inflight` 里选择 16 到 1024 之间的值，随 `initialize` 发给插件。插件在读到它之前不会发出自己的请求（`Start` 在处理 `initialize` 的过程中才运行），所以插件的会话先按最大值建立，在收到 `initialize` 时由会话层接管宿主的选择；宿主一侧的会话层拒绝发出与自身上限不同的 `initialize`。两端因此不可能各持一个值。

没有让插件声明自己的上限再取较小者：插件处理不过来时应当自己排队或拒绝，而宿主才知道这台机器要承载多少。

其中 8 个名额留给会话自身的控制请求（订阅、子实例等），与原先相同；业务调用可用的是上限减 8。超过的调用方等待名额，链的一跳不等待而以 `not_ready` 失败，这些行为不变。

### 观测是一个回调，不是指标库

`OnCall func(CallRecord)` 在调用方的 goroutine 上、状态锁之外调用，带 entry、activation、服务、方法、是否为流、条目数、耗时和调用方得到的错误。应用把它接到 Prometheus、OpenTelemetry 或别的系统；框架不依赖其中任何一个，也不记录请求与响应的内容。

实例状态的变化已经可以通过内核的 `InstanceChanged` 事件得到，不重复提供。

## Risks / Trade-offs

- [上限调大后一个慢插件占用更多宿主 goroutine] → 上限有 1024 的硬顶；默认不变。
- [回调阻塞会拖慢调用方] → 文档写明须及时返回；与日志出口的约定相同。

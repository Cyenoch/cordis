# Design

## Context

动机见 proposal.md。前置：`rebase-native-on-kernel`：两侧都运行内核，可跨进程的键在 `contract`。

与本设计相关的协议事实（`wire`）：

- 基础帧种类是请求、响应、取消；流增加数据项帧与额度帧（决定 2）。一个请求恰好对应一个响应；重复的响应会使会话失败。
- 每个请求有期限，默认 30 秒，上限 120 秒。
- 每个方向最多 64 个在途请求；已取消但未答复的请求另有预算。
- 取消只能由调用方发给被调用方，被调用方必须在宽限期内答复。
- `parent` 字段把一个请求关联到对端的某个在途请求，并继承其期限与取消。反向调用靠它实现。
- 所有帧共用一个发送队列；按请求的流量控制由流的额度提供。
- 生成的服务把方法复用在一个端点上；`contract.Endpoint.Call` 是一问一答。

## Goals / Non-Goals

**Goals:**

- 结果流逐项到达、有界缓冲、可提前停止，跨进程与同进程表现一致。
- 中间件链跨进程时保持内核 `Chain` 的语义：次序、`next` 至多一次、取消传递。
- 作者写的代码不出现协议概念：流就是 `iter.Seq2`，链就是 `Use` 和 `Do`。
- 不使用这些特性的插件和会话路径不受影响。

**Non-Goals:**

- 调用方上传流和双向流。
- 改变期限上限、在途上限或帧预算。
- 跨进程传递函数值或对象引用。

## Decisions

### 1. 流的 Go 形状：`iter.Seq2[T, error]`

作者声明里方法增加 `stream = true`，其 `response` 描述单项的类型。生成的接口方法：

```go
Watch(ctx context.Context, req WatchRequest) iter.Seq2[WatchItem, error]
```

- 实现方返回一个迭代器，在其中 `yield` 各项；`yield` 返回 false 表示消费者已停止。
- 消费方 `for item, err := range client.Watch(ctx, req)`；`err` 非空表示流以错误结束，是最后一次迭代。
- 请求在开始迭代时发出，不迭代就不产生调用。

`contract.Endpoint` 增加：

```go
Stream(ctx context.Context, method string, input json.RawMessage) iter.Seq2[json.RawMessage, error]
```

备选与否决理由：

- 返回 channel：需要约定谁关闭、错误走哪条路，提前停止容易泄漏 goroutine。
- 回调参数 `func(item) error`：不能与标准库的迭代器工具组合。
- 把全部结果放进一个响应：不能逐项到达，且受帧预算限制。

### 2. 流的协议：数据项帧与额度帧

- 请求帧增加 `stream: true` 与 `window`（初始额度）。
- 新帧种类 `item`：被调用方到调用方，带请求编号与单项负载。
- 新帧种类 `credit`：调用方到被调用方，带请求编号与追加的额度。
- 响应帧结束该流：负载为空表示正常结束，带错误表示失败。
- 取消帧终止该流；被调用方照常以响应答复。

流量控制：

- 被调用方已发送未获额度的项数不得超过当前额度；额度用尽时它的 `yield` 阻塞。
- 调用方每消费掉窗口的一半就追加相应额度，把额度帧的数量控制在项数的常数分之一。
- 默认窗口为 16 项，由调用方在请求里给出，上限 256。
- 调用方为每个流持有的缓冲不超过窗口大小，因此总内存以“在途流数 × 窗口 × 帧预算”为界。

期限：流请求的期限由调用方执行，只在被调用方持有额度（也就是轮到它发送）时计时，每收到一个数据项重新计时，额度用尽时暂停。它约束的是“被调用方该发而没发”的时间，仍受 120 秒上限限制；调用方自己消费得慢不会使流超时。被调用方不按帧间隔计时，它在等待额度时只受取消、会话结束和实例停止的约束。整个流的时长由调用方的 ctx 决定。需要长时间不产生结果的 provider 应周期性产生心跳项，此时它持有额度，可以发送。

在途名额：一个流从请求到结束占用一个名额。不单独设流的上限。

单项超过帧预算时，被调用方以错误结束该流，不影响会话，与“普通响应过大只失败当前调用”的规则一致。

读循环上的处理：数据项和额度帧只做入队与计数，不执行业务回调，符合“读循环不阻塞”的约束。

迟到的帧：

- 调用方取消或提前停止后，对端可能已经发出至多一个窗口的数据项。会话把已取消的请求记在一张有界的历史表里；属于这些请求的数据项被丢弃，直到其结束响应到达。
- 既不在途也不在取消历史里的编号上的数据项、超出额度的数据项，按协议错误使会话失败。
- 流结束后才到达的额度帧被忽略：额度可能与结束响应在途中交错。

### 3. 同进程的流

同进程直连时客户端直接返回实现方的迭代器。提前停止经 `yield` 返回 false 传达，错误经第二个返回值传达，因此不需要额外机制即可与跨进程表现一致。输入校验照常执行。

### 4. 跨进程中间件链

`contract.ChainKey[In, Out]` 的操作与内核的 `Chain` 对应（`Use`、`Do`），内部是输入输出均为 `json.RawMessage` 的内核链加编解码。和 `contract.EventKey` 一样，`Use` 带 ctx 并返回取消函数与错误，因为在 guest 进程里登记是一次可能失败的往返；它在作用域里查找上行链路：取不到时作用于本进程内核，取到时经会话交给宿主。

宿主内核上的那条链是唯一的次序与 `next` 至多一次的决定点。

| 方法 | 方向 | 作用 |
|---|---|---|
| `chain.use` | guest 到宿主 | 登记一个中间件，带登记身份、链名和选项；宿主在该 entry 实例的作用域上登记一个转发中间件 |
| `chain.unuse` | guest 到宿主 | 取消登记 |
| `chain.invoke` | 宿主到 guest | 执行某个已登记的中间件，带输入 |
| `chain.next` | guest 到宿主 | 中间件调用 next，带 `chain.invoke` 给出的调用令牌，宿主据此找到要继续的那次执行 |
| `chain.do` | guest 到宿主 | 发起一次执行，带链名与输入 |
| `chain.final` | 宿主到 guest | 执行发起方的最终处理，带 `chain.do` 请求里由 guest 给出的调用令牌 |

- 转发中间件收到内核给的 `next`。它为这次调用生成一个令牌，随 `chain.invoke` 发给 guest 并登记“令牌对应的 next”；guest 的 `chain.next` 带着令牌到达时调用它。内核已保证 `next` 至多一次，第二次的错误原样返回给 guest。
- 关联用负载里的显式令牌，不用 `parent`：`parent` 取自调用时的 ctx，只认同一端点上最内层的在途请求；中间件用别的 ctx 调用 next 时它会指向错误的请求或丢失，而无效的 `parent` 会使会话失败。`parent` 仍然照常携带，只用于传递期限与取消。
- `chain.invoke`、`chain.next`、`chain.do`、`chain.final` 不受一问一答请求的 120 秒期限上限约束：一次链执行可能包含长时间的工具调用。它们的时长由发起方的 ctx、取消、会话与实例的生命周期决定。
- 会话在 `chain.invoke` 期间结束时，转发中间件先等它已经发起的 `next` 调用返回，再把会话错误交给上游，保证 `Do` 返回时最终处理不再运行。
- 登记身份沿用订阅的编号规则，归属取自会话绑定的 activation。
- 中间件所在进程在 `chain.invoke` 期间结束时，该请求以会话错误结束，转发中间件把它连同实例信息返回给上游。

每个跨进程的中间件增加两次往返（invoke 与 next）。链上有 n 个跨进程中间件时，一次执行占用的在途名额与嵌套深度成正比。

### 5. 特性协商

- 新增特性名 `streams` 与 `chains`。协议 major 1、minor 0，两项特性经特性协商而不是版本区分。
- 包的 manifest 在声明了流式方法时把 `streams` 列为必需特性；`chains` 由 SDK 在首次使用链时检查 `initialize` 带来的宿主特性，对端不支持则 `Use` 或 `Do` 返回错误。
- 宿主与 SDK 都声明支持两者。

### 6. 测试

- `wire`：额度不足时发送方阻塞、额度帧恢复、取消终止流、乱序或越额的数据项使会话失败、单项过大只失败该流、流占用与释放在途名额。时序用 `testing/synctest`。
- 端到端（内存会话）：规格中流和链的每个场景，同进程与跨进程各一份。
- 真实进程：一个流式示例插件和一个中间件示例插件纳入 conformance。

## Risks / Trade-offs

- 帧种类增加后，读循环上的顺序规则更复杂 → 新帧只做入队与计数；越额、未知编号、流结束后的数据项一律按协议错误使会话失败，并有对应测试。
- 慢消费者占住在途名额 → 名额上限不变；文档写明长时间的流会占用名额，需要大量并发流时应合并或分页。
- 持有额度却长时间不产生结果的流会被调用方判为超时 → 文档说明；需要长时间静默的 provider 应周期性产生心跳项。
- 跨进程中间件的延迟随链长增加 → 文档给出每跳的往返次数；高频路径建议把中间件放在同一进程。
- guest 在 `chain.invoke` 返回后才调用 next，令牌已经失效 → SDK 在中间件返回后使其 `next` 失效并返回错误，不发送请求；宿主对未知令牌返回错误而不终止会话。
- 链的请求不设期限上限，挂起的中间件会长期占用在途名额 → 发起方的 ctx 取消会沿链传递；文档建议发起方总是带期限。

## Open Questions

- 默认窗口 16 是否合适，取决于真实负载。它是调用方的参数，调整不改变协议与规格。

## Context

源码事实（`195e9c0`）：

- `schema/references.go` 在编译前展开 `#/$defs/Name` 与 `#/types/Name` 引用。`resolver` 带三项限制：32 层深度、10000 节点、1 MiB 累计字节（`maxResolvedBytes`）。
- 计费点有五处：
  - `resolve` 先拒绝原文超过 1 MiB 的文档；
  - `expandRoot` 按原文长度计费；
  - `expand` 在每个节点入口按该节点原文长度计费；
  - 每层把子节点重新编码的 `marshalObject` 和 `oneOf` 按输出大小计费；
  - 原文包括空白。
  所以一个叶子的字节在每一层祖先的入口和出口各计一次。
- `Definition.normalized()` 为一份契约建一个 `resolver`，类型、服务方法的请求与响应、definition 配置依次经它展开，共用预算和节点计数；每份展开结果随后由 `Compile` 用独立的 resolver 再检查一次。`schema.Compile`、包级 `Check`、`Validate` 每次只处理一个 schema。
- `schema.Parse` 由三处调用：
  - `gocontract` 在 `Package.current()` 读取被导入包（可能来自其他 module）的 `cordis_gen.json`；
  - `packagehost` 读取作者的契约；
  - `cmd/cordis generate` 读取用户给出的契约文件。
  `Parse` 是导出 API，输入可能来自依赖或对端，它必须独立于调用方约束自己的工作量。
- `gocontract` 先对推导出的 schema 做一次 `Normalized()`，再把规范结果用 `json.MarshalIndent` 写成 `cordis_gen.json`，不检查写出的内容能否被 `Parse` 读回。推导出的对象没有 `"additionalProperties":false`，规范化后每个对象多出 29 字节（含逗号），所以写出的契约比第一遍处理的大。
- `wire` 的 `handle` 把处理函数返回的带码 `*contract.Error` 原样放进响应，`readFrame` 接收任意字符串错误码。`schema/session.schema.json` 中响应的 `error.code` 却是 11 个值的封闭枚举，而同一文件的 `$defs/failure.code` 是 `{"type":"string"}`。

实测：VortexGo `pluginapi/cordis_gen.json` 共 289,227 字节，198 个 schema 文档，没有 `$ref`。在 `Parse` 路径上，共享 resolver 按旧计费计 1,452,308 字节（预算的 138.5%），节点 1,808 个。按本变更的计费为 92,368 字节（8.8%），即这些文档紧凑编码的总和；节点数不变。

## Goals / Non-Goals

**Goals:**

- 预算约束真正的资源：展开结果的大小，并由它约束展开的工作量。计费与空白和嵌套深度无关，每个产出字节只计一次。
- 引用放大（billion laughs）仍在复制发生前被拒绝。
- 生成器不写出自己读不回的契约。
- 会话 schema 接受运行时实际发出的响应。

**Non-Goals:**

- 提高 1 MiB、32 层或 10000 节点中的任何一项。
- 改变节点的计数方式（它已经是每个产出节点计一次）。
- 改变 `packagehost` 对清单中每个 definition 配置单独 `schema.Check` 的方式。
- 为错误码规定格式。

## Decisions

### 按复制进结果的紧凑字节计费

**规则。** 只在两处计费，计的都是紧凑编码的 `encodedSize`（含 `<`、`>`、`&` 与 U+2028/2029 在重新编码时被转义的增长）：

- 根文档在 `resolve` 入口计一次（先校验 JSON 并紧凑化）；
- 每次引用访问，在展开目标前计目标值一次。目标为 `#/$defs/Name` 或 `#/types/Name`；类型的值连同它的 `$defs` 一起计。

`expandRoot`、`expand`、子节点重新编码和 `oneOf` 不再计费。共享的 `types` 在构造 resolver 时紧凑化一次，引用计费因此不受文件缩进影响，也不会对同一段空白反复扫描。

**为什么能约束大小。** 展开结果中的每个字节，要么来自根文档，要么来自某次引用复制进来的目标值。重新编码只可能因转义而变长，`encodedSize` 已计入这部分。所以计费总额不小于所有展开结果的大小之和，包括为校验 `$defs` 而展开、随后丢弃的结果。

多计的部分有三类：被替换掉的 `{"$ref":…}` 本身、类型的 `$defs`、根文档中的 `$defs`。它们与输入成正比，而且每次引用都会重新读取、校验，计入是对实际工作的如实计量。

**为什么能约束工作量。** 每一层要解码自己的输入、重新编码自己的输出。同一深度上的节点互不重叠，嵌套最多 32 层，所以编解码的总字节数不超过计费总额的约 2×33 倍；内存中同时存活的副本与展开结果同阶。旧做法试图把所有中间副本之和压在 1 MiB 内，结果是：

- 一个紧凑后 92 KB 的契约因为平均嵌套深度被计成 1.45 MB；
- 同一份契约，缩进写出时的计费比紧凑写出时高。

**引用在复制前计费。** 一个 1 KB 的 `$defs` 链若在每层引用前一层十次，第五层就超过节点上限或字节预算，此时尚未分配对应的展开结果。

拒绝的备选：

- **展开后再测量结果大小**：放大已经发生，内存在检查前就被用掉。
- **只对引用放大计费，根文档不计**：预算就不再约束一份契约展开后的总大小。文档承诺的"超过 1 MiB 的声明在生成或宿主预检前被拒绝"会失效，纯字面的大契约只受调用方输入大小约束。
- **提高上限**：VortexGo 的契约仍会随嵌套加深而触顶；排版改变计费的问题照旧。
- **保留原文长度预检**：它按含空白的原文计算，同一内容换一种缩进就可能被拒绝；紧凑后的根文档已计入预算，它不再保护任何东西。

### 预算以一份契约文件为范围

`Parse`、`Definition.Check`、`Normalized`、`Specs` 中，一份契约的类型、方法请求、方法响应、definition 配置共用一份预算和节点计数，与现状相同。`Compile`、包级 `Check`、`Validate` 以单个 schema 为范围。

理由：类型被所有文档共享，文档数量由输入决定。`{"$ref":"#/types/T"}` 只有 20 字节。如果每个文档各有 1 MiB 预算和 10000 个节点，1 MiB 的契约可以写出约 5 万个这样的文档，展开到约 50 GB。按文件计费，展开总量就被约束在 1 MiB，不论文档有多少。

拒绝的备选：**按服务或方法计预算**。它让一份小文件的展开量随文档数线性放大，失去 `Parse` 面对依赖与对端输入时的保护。

VortexGo 的问题来自重复计费，不来自范围。修正计费后，同一份文件只用掉 8.8% 的预算。

### 生成器在写出前重新解析契约

`Package.Contract()` 把将要写出的字节交给 `schema.Parse`，失败时返回 `<包目录>/cordis_gen.json: the generated contract does not parse: <原因>`。`Generate` 与 `Check` 都经过 `Contract()`，所以两个文件都不写，`Check` 同样失败。

`generated()` 改为先取 `Contract()` 再取 `Source()`（源码事实：`Source()` 调 `Specs()`，把同一份规范定义再规范化一次，消耗同样的预算）。否则同一失败会先在 `Source()` 里报出，错误只指向某个方法的 schema，不指向文件。

这里检查的是与下游读取者完全相同的路径和输入，不另写一套预测。具体失败场景：推导出的契约在 1 MiB 内，规范化补上的 `additionalProperties:false` 把它推过 1 MiB。

拒绝的备选：**只在第一遍用规范形式计费**。它依赖"规范化是写出前最后一步"这一隐含约定；之后生成器或格式再有变化，同类问题会再次出现而无人察觉。

### 应用错误码原样传递

响应 `error.code` 改为 `{"type":"string"}`，与运行时和 `$defs/failure.code` 一致。`docs/protocol.md` 列出 Cordis 自己使用的错误码，说明处理函数返回的带码错误原样送达调用方，没有错误码的错误成为 `plugin_failed`。

这是只放宽的修改：旧 schema 接受的消息，新 schema 都接受。它符合 `docs/stability.md` 对向后兼容的约定，不需要新标识。

拒绝的备选：

- **加 `pattern` 约束错误码**：运行时不检查错误码。要让 schema 与运行时一致，运行时就得改写或拒绝应用的错误码，而这样做没有对应的失败场景。
- **把应用码登记进枚举**：枚举由框架发布，应用的错误码不由框架决定。

## Risks / Trade-offs

- [节点上限成为契约规模的实际上限] VortexGo 当前 1,808 个节点（上限的 18%），字节为预算的 8.8%，所以先触顶的是节点。按当前每节点约 51 字节，契约增长到现在的约 5.5 倍（约 510 KB 紧凑 schema）时达到节点上限，届时错误会说明是深度或节点上限。是否放宽应由届时的实测决定，本变更不预先放宽。
- [超限错误的定位] 预算按文件累计，报错落在用尽预算的那份文档上，它不一定是问题所在。错误文字说明这是累计预算，不再写成某个 `$ref` 超限。
- [允许的工作量比旧做法大] 旧做法把中间副本之和限制在 1 MiB；现在限制的是结果，最坏情况（结果 1 MiB 且每个字节都在 32 层深处）约有 66 MiB 的编解码。上界仍是固定常数，与输入的排版和文档数无关；为了让契约不因嵌套深度被拒绝，这是必要的代价。
- [重新解析的额外开销] 生成时多一次 `Parse`，开销与契约大小成正比，相对 `go list` 与类型检查可以忽略。

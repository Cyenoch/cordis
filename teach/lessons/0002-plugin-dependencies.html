插件依赖插件：三层，别混

“依赖”在这里是三个不同的问题：能不能装（包依赖）、什么时候能跑（服务需求）、谁先停（父子所有权）。用错层，症状都长成“不起作用”。

第 1 层：服务需求——决定“能不能调用”

声明在 Definition.Requires，匹配规则是名字 + major 相同、minor 落在闭区间。发布后再调用：

requiresA := contract.Requirement{Name: "chain.a", Major: 1, MinMinor: 1, MaxMinor: 3}

data, err := scope.Call(ctx, requiresA, input)          // 原始 JSON
// 或类型化：sdk.Call[Request, Response](ctx, scope, requiresA, req)

provider 没出现时，实例照常启用，但状态是 waiting，Status.WaitingFor 里是 chain.a@1；provider 退役后消费者退回 waiting，新 provider 发布后得到新的 activation。绑定在初始化时固定，不会在调用中悄悄换 provider。

第 2 层：包依赖——决定“能不能启用”

manifest 里按包 ID 与严格 SemVer 声明。它检查的是已选择的版本，不是“已安装”：

"dependencies": [{"id": "demo.core", "min": "1.0.0", "max": "2.0.0"}],
"optionalDependencies": [{"id": "demo.extra", "range": ">=1.2.0 <2.0.0"}]

必需依赖缺失、版本不符或成环，Enable 前的 Preflight 直接报错；可选依赖缺失只会写进 Status.Diagnostics，实例仍然 active。

第 3 层：父子——决定“谁先停”

宿主侧用 Entry.Parent，持久、Disable(parent) 停整棵子树。作者侧用 contract.CreateChild，绑定当前 activation：

child, err := contract.CreateChild(ctx, scope, contract.Child{
    ID: "optional", Definition: "middle", Config: scope.Config(),
})
// 只登记，不等待；父发布后再 child.Wait(ctx)。初始化里 Wait 自己的子实例会返回 reentrant_call。

子实例不参与服务依赖解析：它解决的是“这个包的可选功能”，不是“我需要另一个包的服务”。

练习：这次会发生什么？

选项等长，别靠形状猜；点错可以重试，Esc 重置当前题。

① 包 A 的必需包依赖 demo.core 已安装，但从未被选择，宿主 Enable(A)。
Preflight 在启用前跑，报 A requires missing selected package demo.core。安装本身不做依赖检查。
② consumer 要求 chain.a@1 [1,3]，provider 已启用但声明的 minor 是 0。
服务绑定的失败不是启用失败：实例 active 不了，停在 waiting，WaitingFor 里是 chain.a@1。
③ provider 在同一 Host 且已 active（minor 2），consumer 要求 [1,3]。
2 ∈ [1,3]，major 相同，服务已发布：绑定成立，scope.Call 可达。
④ 可选依赖不存在，其余依赖都满足。
可选依赖只产诊断（optional dependency … is not selected），实例照常 active；诊断留在 Status.Diagnostics。
⑤ A 的必需依赖 demo.core 已选择为 2.0.0，但 A 要求 [1.0.0,2.0.0)。
包层是严格 SemVer 半开区间：2.0.0 落在区间外。报错形如 A requires demo.core [1.0.0,2.0.0), selected 2.0.0。（依赖环也在同一处判定，但正常 Select 通常会先把它挡掉。）

回忆：晚到的 provider

先启用 C，再启用 B，最后启用 A（C→B→A 依赖链），每一步分别看到什么？

C 启用后 waiting（等 chain.b@1），B 启用后也 waiting（等 chain.a@1），A 发布后 B、C 依次收敛为 active。examples/plugins/chain 的断言 consumer-first-late-provider 就在验证这条路径，且调用 C 时能看到两层存活资源。

为什么“已安装”不等于“可依赖”？

安装只往 catalog 里放内容；包依赖的匹配对象是 Selected，而选择是宿主的显式动作（Host.Select），安装不会改变选择。所以“装了但没选”在包层是缺失，在服务层也不可能出现 provider。

这一课你该带走的

症状定位顺序：Enable 报错看包依赖与 Preflight；一直 waiting看 WaitingFor、provider 状态与 minor 区间；停用顺序不对看父子所有权。三者互不替代——子实例不解析服务，服务需求也不检查包版本。
